Isolating a coding agent

Five ways to sandbox a coding agent

A coding agent runs arbitrary code and reads untrusted input. Each option below puts the boundary somewhere different — from nowhere at all to one container per identity.

The magenta field on the right is what stays reachable.

The yardstick

Not malice. Reach.

The assumption is not an attacker with a kernel exploit. It is an agent that is wrong — and the fact that anything it reads is something that can instruct it.

One question measures every option:

When the agent does the wrong thing,
how far does that go?

Option 1 · no boundary

The agent runs as the invoking user

An agent launched from a shell inherits the invoking user's uid. Every file that uid can read, it can read: every key, every repo, every credential in the home directory.

Nothing stands between the agent and ~/.ssh except its own judgment about what it ought to touch.

Reach: everything the user owns.

Option 2 · a sandbox assembled by hand

Bubblewrap

bwrap builds a sandbox from Linux namespaces — fresh mount, pid, user and network views for a single process, no root daemon. It is the layer under Flatpak.

What it gives

No daemon, no root — it's just a process
Binds in exactly the paths named
Masks the rest — ~/.ssh simply isn't there

What it costs

The boundary is a flag list, maintained by hand
One missing --bind is a hole in the wall
Agent tooling needs enough holes to turn it to Swiss cheese
Option 3 · a container on your machine

The agent inside a container

The agent moves into a container on your machine: a full OS in a box, with only the working repo mounted. The box can be systemd-nspawn or Docker — the end result is the same.

What it gives

A full OS inside — tooling works unmodified
The boundary is the container, not a rule list
Every session can start from a clean image

What it costs

An image to define, build and keep current
Egress to fetch dependencies widens reach back out
Still your daily machine, one session at a time
Option 4 · a server that holds the agent

A persistent container on a server

A NixOS server runs a persistent container. The agent inside runs as uid 1500 — deliberately outside the host's uid range — on its own private veth network.

SSH, sops and signing keys stay on the host. Secrets enter only as read-only bind mounts under /run/secrets.

Option 2 returns as depth: each session runs under bubblewrap inside the box, seeing only its worktree and tooling. An agent that is wrong meets that wall before the container's.

Reach: a worktree, then the container.

Option 4 · getting code out

Getting code out

The agent has to push. There are two ways to allow that, and they trade the same thing against each other.

Inject a scoped token

Reach on GitHub is an explicit repo allowlist, guarded by a branch ruleset
A live credential exists inside the box

Inject nothing

Reach on GitHub is zero
A human reviews, pushes and merges every change by hand

This option takes the token.

Option 4 · access

One door

Inside the box an orchestrator daemon listens on 127.0.0.1:6767. The only route in is tailscale serve — a single door published to a tailnet, password required.

Any device on the tailnet is a thin client. Each session gets its own git worktree inside the box, and the code never leaves it.

Reach on the network: one port.

Option 5 · one container per identity

Split the box by identity

One box holding two contexts shares a filesystem and a token between them: a poisoned file in a work repo is read by an agent holding the personal credential. Splitting the container ends that.

Each box is scoped to one identity — one GitHub user, work apart from personal, one AI account apart from another:

Its own GitHub token — a different fine-grained PAT with a different repo allowlist
Its own signing key — a commit's signature identifies which box made it
Its own agent user and filesystem — separate home, separate repos, separate worktrees

An injection reaches the wall and stops.

A worked example

Keys on the host. Repos in the box. Code on GitHub.

The top options combined: two containers on a server, each scoped to one identity — one credential, one signing key — with an orchestrator serving each box to the tailnet, so any device is a thin client.

The agent's behaviour is the same in every option.
Only its reach changes.
