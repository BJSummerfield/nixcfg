# T9 — flake.nix does one thing again

`invariant: drvPath` for hosts and packages (byte-identical, no exceptions).
The `checks` set may move, but must stay the same 15 checks — see below.

**Promoted from last to second (2026-09-04, user request.)** The user's framing:
before this repo grew agent tooling, flake.nix "was literally just where I
declared my host files." That is the target.

## Why now, not after GATE 2
The checks block is self-contained. It does not depend on the ledger, the
comment diets, or the renames, so the argument for doing it on a clean base
does not apply to it. Meanwhile every task between now and GATE 2 would pile
onto a file that is already 45% machinery — T1 alone added ~40 lines.

## The measurement that justifies this task
flake.nix at 69de814 is 247 lines:

| section | lines | share |
|---|---|---|
| `checks` (eval matrix, tests, lint checks, caddy adapt) | ~110 | 45% |
| `inputs` | ~40 | 16% |
| `nixosConfigurations` + `darwinConfigurations` | ~43 | 17% |
| `packages`, `devShells`, `formatter` | ~36 | 15% |

Host declarations are 17% of the file that exists to declare hosts. The check
matrix is 2.5x the size of every host declaration combined. Rubric B5: the file
cannot state its purpose without "and".

## Target shape
flake.nix keeps `inputs`, `nixosConfigurations`, `darwinConfigurations`, and the
thin wiring that reads the extracted files. Everything else moves out. Suggested
— you own the final layout, but justify any departure:
- `checks/default.nix` — the eval matrix, the lint checks, the caddy adapt
  check, and the imports of `tests/`. It is one responsibility: "prove the repo
  is correct."
- `packages/default.nix` — the three `callPackage` lines. The derivations
  already live in `modules/*/package.nix` (rubric B7); this is only the wiring.
- `devshell.nix` (or similar) — the devShell and its tool list.

Each extracted file takes what it needs as arguments. Do not introduce a
global `let` that re-creates the coupling you just removed.

## flake-parts
PLAN.md said to evaluate flake-parts and reject it explicitly if the dependency
is not worth it. **The orchestrator's position, which you should adopt unless
you find a concrete reason otherwise: reject it.** Moving a `let` block into
`checks/default.nix` does not need a framework, and flake-parts is a new input
to track, a new idiom for every future reader, and a rewrite of working wiring.
State the rejection and the reasoning in one short paragraph in your summary.
If you think that is wrong, argue it — but do not adopt it silently.

## Comments
The user has said, explicitly and twice, that flake.nix's comments look bad.
Rubric A applies with full force here and this file is the worst offender for
it. In particular: **no comments inside `''` shell blocks.** If a shell step
needs explaining, the explanation goes above the derivation. Delete anything
that restates code or justifies an uncontroversial choice. Do not add a
banner comment to each new file explaining what its filename already says.
