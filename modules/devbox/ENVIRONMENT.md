# Environment: persistent devbox container

You are inside a long-lived NixOS container (systemd-nspawn). The container is
the security boundary; no sandbox wraps your commands.

- The container persists across sessions and host reboots: your home, shell
  history and anything installed by hand are still here next time. It is not
  self-cleaning scratch space.
- Projects live in `/home/agent/projects`, paseo worktrees in
  `/var/lib/paseo/worktrees`. Neither is bind-mounted from the host, so
  uncommitted work is backed up by nothing. Push anything you care about.
- Your config is generated by the host's nix configuration: pi's under
  `~/.pi/agent`, claude's under `~/.claude-state` (`CLAUDE_CONFIG_DIR`; there
  is no `~/.claude`). Editing those files in place does not persist and can
  break the next host activation. Durable instructions belong in the
  repository's `AGENTS.md` / `CLAUDE.md`, which every spawned subagent
  inherits. Config that must change globally is a request to the user, not a
  local write.
- The one writable exception: claude's per-project `memory/` directory under
  `CLAUDE_CONFIG_DIR` survives rebuilds and sessions. pi has no writable
  counterpart.
- `/tmp` is a RAM tmpfs, wiped on reboot, capacity is memory. `/var/tmp` and
  the checkouts are disk and survive. Never put anything large or needed later
  (a `CARGO_TARGET_DIR`, a build tree) in `/tmp`; ENOSPC there kills builds and
  running processes alike.
- Missing tools: `nix shell nixpkgs#<pkg>` or `nix-shell -p <pkg>` (the store
  is shared with the host, so anything it has costs no download). npm/pip/cargo
  also work. There is no sudo and you will never need it.
- Refer to tools by package name, never by an absolute `/nix/store/<hash>-...`
  path: garbage collection deletes unreferenced store paths, so a recorded hash
  works until it abruptly does not. Resolve the path at use time.
- Git push/pull/clone authenticate through a credential helper reading a GitHub
  PAT; `gh` gets `GH_TOKEN` from the same secret. The token is scoped to
  specific repositories, so an auth or permission failure usually means the
  repo is out of scope: report it rather than retrying.
- You have unrestricted network access.
